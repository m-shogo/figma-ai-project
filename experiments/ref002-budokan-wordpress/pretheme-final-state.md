# REF-002 Pre-Theme Final State

Date: 2026-08-23
Base target: `so`

## State reached before the production Theme is supplied

The pre-Theme phase is complete when all work that does not depend on the actual production Theme has been externalized and no implementation architecture has been invented in its place.

Completed:

- live Figma PC/SP section observation
- Figma Parts inventory and page-family mapping
- Block Editor ownership candidates
- Theme-adaptive resolution order
- discover-before-ask policy for Theme reconnaissance
- supplied-Theme intake fail-closed boundary
- WordPress + ACF PRO disposable runtime reuse plan
- CMS mutation / visual / typography / asset-lineage QA reuse plan
- protected REF-002 baseline retained only as comparison evidence
- exact durable Figma raster source pinned for selective reuse with SHA-256
- old benchmark HTML/CSS/JS explicitly excluded from production architecture authority
- SP -> PC acceptance order and shared-owner invalidation inherited from the canonical frontend policy
- Before/After measurement dimensions defined in `theme-adaptation-plan.md`

## Remaining external inputs

Production implementation must not start until the actual Theme is supplied.

Required from outside this repository:

1. production Theme repository/commit or equivalent Theme source access
2. company/project policy that is not present in that Theme repository, if any
3. business/editorial requirements that code/runtime evidence cannot determine

Everything observable from the Theme must be discovered by the agent before asking the user.

## First action when Theme arrives

1. pin Theme repository + starting commit
2. run existing read-only target reconnaissance/readiness tools
3. classify Classic / Hybrid / Block from evidence
4. observe templates, blocks, patterns, styles, assets, ACF, CPT, form and JS/CSS conventions
5. update `theme-intake.yaml` from UNKNOWN/UNDETERMINED using evidence only
6. resolve ownership and freeze the intake
7. selectively import required exact Figma assets and re-hash them
8. create fresh section runs from the canonical run template
9. implement/accept in SP -> PC order
10. complete Block Editor, CMS mutation, Full Page and Human Editability QA
11. compare against the old baseline and capture reusable lessons without auto-promotion

## Stop condition

Until the production Theme exists, additional PHP/CSS/JS implementation would be fabricated architecture rather than progress.

Therefore the only legitimate blocker at this point is external Theme/business input, not missing project foundation.
