# Recurring Agent Work — 新チャット/新案件の開始時チェック

Status: **HUMAN-APPROVED OPERATING CONTRACT**（2026-11-20）
Scope: **CROSS-PROJECT / OPERATING PRACTICE** — このrepoで扱う **定期実行・毎時実装・継続作業**。案件個別の技術仕様やセキュリティ規則を上書きしない。
Owner: Human が明示指定。詳細な実行方針は `docs/agent-execution-policy.md`、案件正本は `projects/<slug>/docs/`。

## 0. 新しいチャット・新しい案件の **最初** に確認・指摘する

毎時/毎日/定期スケジュールを新規作成・移管・再開・編集する前、または既存の定期タスクを別チャットで引き継ぐ前に、以下を確認する。

1. **「毎時」= 1時間ごとの起動機会**。1回50分の実行を保証する設定ではない。長時間の連続作業を行う場合は、その実行環境で可能な時間・ツール制限を別途確認する。
2. **「1単位」= 安全な変更/レビュー/コミット/PRの粒度**。1時間に1単位という意味 **ではない**。同じ回で何単位も進めてよい（実行可能なら進める）。
3. 最初に最新の base SHA、open PR、別Agentのowner、最新仕様・QAチェック・既存の学習ログを確認。未マージの先行成果を重複実装しない。
4. **定期タスクの実行履歴**（可能なら開始/終了時刻、成果、阻害要因）を見て、指示が意図どおり実行されているか検証する。起動回数を稼働時間とみなさない。推定作業時間を実測値として報告しない。
5. 初回に Human の期待と仕組みが食い違っている場合は、**作業開始時にこちらから短く指摘**する。Human に「どうして一つしか進めないの？」と言わせるまで待たない。たとえば「毎時は起動頻度で50分稼働の保証ではありません。1回に複数単位を進め、実際の稼働と成果を確認します」。
6. このルールは**案件固有の設定をコピーする指示ではない**。技術実装順・Figma URL/branch/ACF契約・スケジュール自体は新案件で再確認し、新案件に勝手に流用しない。

## Frontend案件の開始時はデザインFoundationも先行確認

FigmaからWeb/WordPress/React/LPを実装する新しい案件では `docs/frontend-foundation-preflight.md` も開始時に読む。**色コード、font/weight、asset/SVG、icon、spacing、breakpoint、共通部品を既存Theme/Design Systemへマッピングし、必要なものを導入・検証してから各パーツに着手**する。カラー表やCSS変数だけ書いて完了としない。既に検証済みのFoundationは再実装しない。テーマはサンプルか案件の正本かを必ず区別する。jwsnjの具体的な値・`nowrap`禁止等を他案件へ自動コピーしない。毎時内にこの基盤作業を複数単位続けてもよい。

## 1. 毎回の実行ループ

```text
Current authority / owner / previous run result / open PR を読む（差分優先）
→ 今回の実行で安全に進められる複数の作業を特定
→ Figma・コード・asset・runtime evidenceを確認（必要な場合）
→ 1つの意味ある変更 + 関連QA
→ 小さくcommit / push / PR / CI / merge（安全条件が揃う範囲）
→ 次の独立した作業へ進む
→ 実行環境の上限・真正のBLOCKED・品質上の停止まで続ける
→ 成果・未検証・終了理由・次の一手を記録
```

- **1回の実行中に複数単位、複数commit/PRも可**。ただし関係ない変更を1commitに混ぜない。安全な単位で区切ることと、1回の作業量を制限することは別。
- Figmaのカラー変数1セット・仕様書1枚のような小変更を終えたら、CSS読み込み/見た目の確認、フォント、画像、次のコンポーネント等の **関連する価値ある次工程**に続けて進む。
- CI待ち・外部依存待ちなら、競合しない独立作業へ切り替える。まだ実行できる作業があるのに「1単位終わったから終了」としない。
- 短い実行で成果が少なかった場合、まず実行時間・ツール/権限制約・不要な再調査・過剰な報告・早すぎる終了条件を検証し、**改善できるボトルネック**を次回のループへ反映する。
- 検証不能な状態で無理にmergeしない。静的チェックとWordPress/ブラウザ実機のQAを混同しない。
- 先にプロジェクトの既存規約・チェックシートを活用。毎回全文を再取得するより、変更履歴・前回からの差分を重視する。調査・文書作成だけで終わらず、実行可能な実装とQAを進める。

## 2. 実行効率を上げる4つの仕組み（Agent提案 2026-11-20）

### A. 次に進める作業を常に用意する — READY / BLOCKED / NEXT

- 案件の既存 `CURRENT_AUTHORITY.md` / `DESIGN_FOUNDATION.md` / 作業記録等、**すでにある1箇所**に、次回すぐ着手できる `READY` 候補を**最大3件程度**記す。候補は「成果物」「影響ファイル」「依存/阻害」「完了条件・確認方法」の最小限。初回に長大なWBSを作らない。
- 現在の `READY` が完了・CI待ち・依存待ちになったら、次の `READY` に進む。依存待ちは `BLOCKED（理由・解除条件・担当）` と明記し、独立作業まで止めない。
- 作業終了時は `READY / BLOCKED / NEXT` を最新にし、次回Agentが長い議論なしに着手できる状態を残す。更新すべき変化がなければファイルを機械的に書き直さない。
- 1時間の上限3件という意味ではない。3件は**再開判断の候補数**であり、さらに進められるなら候補を補充して継続する。

### B. 変更の波及範囲でQAを選ぶ

- **共通トークン/フォント/コンテナ/ナビ**を変更したら依存するPC/SP画面や状態まで検証を広げる。単独カード・文言など局所変更なら関係する画面/状態の検証を中心に行う。優先順位は「利用箇所の数 × 壊れた時の影響 × 戻しにくさ」で判断する。
- 既存 `docs/frontend-maintainability-qa.md` の `FAST PR GATE / TARGETED MUTATION / DEEP / PERIODIC` を使う。**全テストを毎回実行するために開発を止めず、重大リスクの検証も省かない**。実行できないものは未検証と記録し、証拠を捏造しない。
- ローカルブラウザにアクセスできない場合、静的検証を実施した事実だけを記録。**コード・CIがPASS ≠ ブラウザ・実機・Figma一致がPASS**。

### C. 早く再開するための最小引き継ぎ

各回の終了時に既存の案件作業記録またはPRに **「基準SHA / 済み / 未検証 / READY 1〜3件 / BLOCKEDと解除条件 / 最新PR」** を短く残す。次回はこの情報を入口に、その後で `so` 最新状態・Figma・ownerを再確認する。新しい日誌ファイルを毎回生成しない。

### D. 改善が効いたかを検証する軽量レビュー

- 同じ案件でHumanが**同じ種類の手戻りを再指摘したか**、同一原因で修正PRが再オープンしたか、検証未了のまま完了宣言したか、作業終了理由を説明できたかを振り返る。単位数/コミット数/稼働分数だけを成果KPIにしない。
- 同じ原因が**2回続いた場合**、実装より先に失敗した検出・作業手順を見直す（`docs/agent-execution-policy.md` の stuck rule に準拠）。検出できた証拠がなければ「改善成功」と断言しない。
- 改善案はまず案件の `LEARNINGS.md` に実例・原因・有効性を残す。Humanが共通利用を指定したか、`docs/knowledge-promotion.md` のレビューを通ったものだけ、適用範囲付きで `docs/` に整理する。**ルールが増えるほどよい、とは考えない。**

## 実行環境・停滞復旧の入口ゲート（Agent追加 2026-11-20）

### まず「使える作業レーン」を実測する

作業開始時、GitHub等の編集手段だけでなく **ソース編集、依存インストール、PHP/JS build、WordPress起動、ブラウザ撮影、Figma asset取得** のどこまで実行できるかを確かめる。必ずしも全工程を最初の1回で実施するのではなく、対象変更の受入条件に必要な能力を検証する。

| 実行レーン | できる証拠と、できないこと |
|---|---|
| GitHub/Figmaコネクタ中心 | 最新コード・Figma調査、限定的な差分、push/PR/CI。**この環境だけではローカルWordPress表示を検証したとは言えない** |
| CLI/実行環境あり | 依存・構文・build・PHPなどのローカル検証。実際にコマンドを実行した場合のみPASS |
| Browser/WordPress runtimeあり | 画面を表示、操作、スクリーンショット・PC/SP比較。起動できない環境なら未検証 |

- **能力の不足をプロンプトの長さで解決したと主張しない**。必要な品質ゲートを実行できない場合、未検証を明示し、必要なら実装に向いた環境や別レーンをHumanへ提案する。同じwrite scopeに複数Agentが同時に書かない。
- 初回に「今回の対象に必要な検証と現在使えるツールに差があるか」を短く点検。後続の実行では変更した前提だけ確認し、毎回の環境説明を繰り返さない。

### 停滞したPR/作業を復旧する（ルールの追加だけで終わらせない）

- 各回は対象案件の**前回から残るPR、関連CI、mergeable、最新soとの差分**を先に確認。成功したCIと安全な差分・マージ可能状態が揃っていれば速やかにmerge。単にPRを作ったという理由で次回へ先送りしない。
- mergeableがfalse/unknownなら、GitHub側の再計算・base更新・実際の競合を区別。**競合の詳細を見ずにforce/rebaseしない**。別Agentの作業を消さない。
- CIが失敗したら「今回の変更が原因か / soに既に存在していたか」を確認し、既存の `docs/agent-execution-policy.md` §5 に従って分類。無関係なCIを勝手に修正範囲へ巻き込まない。CI failuresを無視して安全性が証明されたとはみなさない。
- 同じPRや同じBLOCKEDが複数回残り、独立したREADYもない場合は、**次の実行で別の解決経路/レーンを検討**し、具体的に「阻害要因・前回と異なる手段・Humanに必要な判断」を挙げる。自動的にファイルだけ増やして前進扱いしない。

### 実機が使えないときは「検証負債」を保留し、再開可能になったら先に返す

- 現在の実行レーンから接続できない**別PC上のローカルWordPress/ブラウザ/有料プラグイン**について、何度も起動に失敗するだけの試行はしない。代わりに案件内の**一元化された Deferred Runtime QA backlog**へ、`ID / 検証対象 / 手順 / 成功条件 / 前提環境 / 実行証拠 / status` を記録する（既存QA台帳があればそれを使う）。
- status `DEFERRED_ENV` は「外部検証待ち」であって、案件全体が `BLOCKED` とは限らない。Figma調査、Theme修正、静的QA、PR/CIなど**現在利用可能な独立タスクを優先的に続行**する。単に起動不可なだけの検証で実装を打ち切らない。
- 実際のローカル環境を使えるレーンへ移ったら、**その実行の最初にDeferred QAを読む**。環境疎通・新しいSHAとの整合性を確認し、**その環境で実行可能になったP0/高リスクの未検証項目を新規実装より優先**して実行。失敗時は復旧/原因を記録し、PASSを偽らない。特に共通Font/CSSやHeaderに波及する未検証を優先する。
- **新機能を作るたびに「どの後日QAが増えたか」を案件台帳へ追記**し、開いていた項目はコード変更に応じて検証し直す。旧SHAのPASSやスクリーンショットを新SHAへ無条件に引き継がない。
- 使用可能状態は毎回の推測でなく、実際のレーンの疎通結果で確認する。**ユーザーが今は使えないと指定した環境**については、明示的に使用可能になったという新情報がない限り繰り返し「今すぐ起動すべき」と提案しない。

### 停滞の検出を曖昧にしない

- 次の実行では、前回の簡潔な引継ぎ記録とGitHubを照合し、同じPR・`READY`・`BLOCKED`について**変化したこと/しなかったこと**を区別する。
- **同一の解除可能な停滞が連続2回以上続く場合**、`STALLED` と原因を記録し、次回実行の冒頭で復旧（CI実行/差分・競合の見直し/Owner確認/別の安全なレーン）を優先する。合理的に`DEFERRED_ENV`またはHumanの後日指示待ちである項目は、停滞と混同しない。
- GitHub Actions・自動監視が存在する証拠のない場合は、**Agentによる開始時点検の検知**と明示。「自動アラートが実装済み」と言わない。反復観測が未実施なら実効性は未検証。
- 実装済み機能、未検証負債の数、PR解消、ユーザー手戻りの実際の推移を追う。記録の件数やルールの行数をKPIにしない。

### 改善が実際に効いたか判定する

ルールを更新した直後は**運用設計の改善**であって、実装速度・First-pass QAの改善実績とは呼ばない。次回以降の複数回の実行記録で、開いていたPRの解消、検証完了した機能、繰り返した調査、未完了/失敗の理由、Humanの再指摘を比較する。**1コミットの行数・1時間あたりPR数は品質KPIにしない**。

## 3. 「50分前後」などの時間指定の扱い

- 50分を希望する指示は **品質のためにまとまった作業をしたいという目的**。予定された自動実行に連続50分の実行時間を発生させる機能だと誤認しない。
- 実行プラットフォームが指定できるのは起動時刻/頻度であって、実行継続時間が設定可能とは限らない。実行時間・トークン・コネクタ権限・非同期性を事実として確かめる。
- 適切な別の実行レーン（例:長い作業に向いたWork/専用実装環境）が必要なら、**最初に**利点と制限を短く説明する。勝手に移管・二重稼働はしない。
- 50分を消化するために待機/無意味な操作をしない。50分実行したと根拠なく主張しない。

## 4. 毎回の簡潔なレポート（証拠優先）

- 開始時の正本 SHA、前回との差分/ownership、実際に確認したFigma node等のevidence
- 完了した **複数の実作業**、検証結果（PASS / FAIL / 未検証）、変更先commit/PR/mergeのURLと最新SHA
- 次へ進めなかった **実際の理由**（時間上限、権限、CI/依存、品質上のBLOCKED等）。推測は推測と明記
- 今回見つけたミス・原因・再発防止（案件 `LEARNINGS.md` / QA checklistへの反映）、次回の最優先作業
- 開始/終了時刻が取れる場合だけ正確な所要時間を書く。未取得なら「不明」。起動間隔からの逆算は禁止

## 5. 実行が期待より短い・成果が少ないときの改善ループ

- 定期タスクの直近の実行ログを確認し、「開始/終了時刻」「具体的成果」「停止理由」「ツール/権限の制限」を分けて記録する。
- 実際に短時間で止まった場合、**「1回1コミットで終了」の誤解や、調査・報告だけで作業が終わる設計**を疑う。実行プラットフォームの制限なのかAgent側の作業終了判断なのかを区別し、次回実行の設計に反映する。
- **新チャット・新案件の初回に、Humanが再指摘する前に**再発しやすい誤解や残る制約を短く説明する。同じ調査を繰り返さず、継続可能な次の変更へ進む。
- 具体的なユーザー発言、日付、実測実行時間、コミットやPR、根本原因などの**個別事例の原本**は案件の `projects/<slug>/LEARNINGS.md` または `projects/<slug>/docs/` に記録する。本書には再利用可能な作業ルールだけを残す。
- 初回の教訓例: `projects/jwsnj/docs/WORKFLOW_LEARNING.md`（案件側の実行記録）。これは運用原則の**出典**であり、新案件の実行時間や個別判断を拘束しない。

## 6. このルールの適用範囲と限界

- **Gitは共通記憶の正本**。新しいAgent/チャットでrepoの`AGENTS.md`と本書を読むことが、運用の再現性の条件。
- このドキュメントをコミットしただけで**ChatGPTの全チャットへ強制配信されるわけではない**。Gitにアクセスできない会話や別repoには自動適用されない。別案件へ移す場合、開始時にリンクして読む/対応するrepoへ明示的に導入する。
- このHuman-approved運用上の規約は `docs/agent-human-fb-weak-spots.md` の W1–W10（UI不具合分類）を勝手に増やすものではない。他の機械的学習昇格規則をバイパスせず、案件の事後評価と両立させる。
