# External Prior-Art Review — Figma × AI Implementation

Last reviewed: **2026-08-11 JST**

Purpose: compare `figma-ai-project` against current public work in Figma-to-code, screenshot-to-code, visual regression, GUI-agent evaluation, and browser-side repair. This is a **research input**, not an automatic best-practice import.

Canonical promotion rule remains:

```text
EXTERNAL SIGNAL
→ RETEST_CANDIDATE
→ local experiment
→ clean replay
→ cross-run/reference evidence
→ promotion candidate
```

Do not change Company Policy merely because another project or paper reports success.

---

## Executive conclusion

The current project is already stronger than most one-shot design-to-code projects in the areas that matter for production reuse:

- Company Policy precedence
- Existing Codebase / Design System reconnaissance
- frozen Reference + lineage
- Required Device / Browser Environment profiles
- section-first progressive disclosure
- boundary / cluster / full-page integration evidence
- immutable First Pass evidence
- targeted repair separated from Clean Replay
- safe parallel execution and Git isolation
- automated upstream Radar

The strongest external ideas that are **not yet fully represented** are:

1. **Behavioral correctness as a separate proof dimension** — a page may render correctly and still have broken interactions.
2. **Capture stability proof** — a screenshot should be taken from a settled state, not merely after an arbitrary wait.
3. **Relative visual comparison as a diagnostic** — pairwise A/B preference can supplement noisy absolute visual scoring.
4. **Browser-runtime repair context** — DOM, computed CSS, source/component ownership and traces can shorten targeted repair.
5. **Direct Code Connect release monitoring** — Code Connect is changing quickly enough to deserve its own official Radar source.

Only (1) schema support and (5) Radar coverage are immediate adoption candidates. (2)–(4) should be experimented with on real references before becoming mandatory production gates.

```text
Global reconnaissance
→ Section Discovery
→ per-section structure profile
→ progressive disclosure
→ Existing Code / Design System reuse
```

### Decision

**KEEP / VALIDATED.** No new architecture needed.

## 2. Figma Code Connect — official

Sources:

- https://github.com/figma/code-connect
- https://github.com/figma/mcp-server-guide/blob/main/skills/figma-generate-library/references/code-connect-setup.md

Code Connect gives Dev Mode/MCP the real production component and prop mapping instead of an autogenerated approximation.

Important current change observed in **Code Connect 1.5.0, released 2026-07-29**:

- parserless/template format is the forward path
- legacy framework-specific parsers stop active maintenance after **2026-08-17**
- `figma connect preview` can inspect and render explicit prop/variant states

### Opportunity

The existing Radar watches Figma release notes and MCP docs but did not directly watch `figma/code-connect` releases.

### Decision

**ADOPT NOW:** add official Code Connect releases to the FIGMA Radar lane.

Do **not** globally force Code Connect into every project; availability still depends on company plan, existing design system, and project policy.

## 3. Figma Simple Design System (SDS) — official

Source:

- https://github.com/figma/sds

Useful patterns:

- Variables + Styles + Components + Code Connect + React shown together
- Storybook colocated with code components
- some code layout primitives intentionally have no one-to-one Figma component
- scripts for tokens/icons/dev resources
- `documentUrlSubstitutions` keeps Code Connect templates portable between duplicated Figma files

### Lesson

Figma structure should not be naively mirrored into one DOM/component per Figma node. Some implementation-only layout primitives are valid and desirable.

### Decision

**KEEP CURRENT HYBRID / CODEBASE_FIRST model.**

Potential future experiment: when a real project uses Code Connect, test `documentUrlSubstitutions` and parserless templates as a portability pattern.

## 6. Design2Code — Stanford SALT benchmark

Source:

- https://github.com/NoviScl/Design2Code

The benchmark contains hundreds of real web pages and uses a fine-grained evaluation breakdown including block matching, text, position, color and visual similarity. It also compares direct prompting, text-augmented prompting and self-revision.

### Lesson

A single visual score hides failure mode. Element/block presence and layout/position can fail independently of color or typography.

### Comparison

Current rubric already separates:

- geometry/layout
- spacing
- typography
- color/effects
- assets/layering
- structural fidelity
- robustness

### Decision

**NO SCORE WEIGHT CHANGE BEFORE REAL RUNS.**

Candidate experiment: add element-presence/recall and layout-structure diagnostics if the first references show repeated omission errors.

## 7. UI2Code^N — ICML 2026

Source:

- https://github.com/zai-org/UI2Code_N

Key ideas:

```text
Draft
→ Render
→ Visual inspection
→ Iterative polish
```

More importantly, the project argues that **absolute visual evaluators are noisy** and uses relative pairwise/tournament visual ranking (RVPO).

### Comparison

The project's existing:

```text
RUN A FIRST PASS
→ FINAL
→ RUN B CLEAN REPLAY FIRST PASS
```

already creates natural paired candidates.

### Decision

**EXPERIMENT CANDIDATE, NOT CORE SCORE YET.**

Add a future diagnostic experiment:

```text
PAIRWISE_VISUAL_PREFERENCE
RUN A First Pass vs RUN B First Pass
```

Keep the existing absolute `/80` rubric for auditability. Relative judgment should supplement, not replace, deterministic measurements and human-visible evidence.

Promotion condition: pairwise judgment must improve agreement with human review across multiple References and must not become the sole pass/fail gate.

## 8. PlayCoder — FSE 2026

Source:

- https://github.com/Tencent/PlayCoder

It separates:

- `Exec@k`: application executes
- `Pass@k`: tests pass
- `Play@k`: GUI behavior actually works through interaction

The project explicitly demonstrates silent failures where code executes and tests pass while actual GUI behavior is wrong.

It also records trajectories and uses diagnosis → patch → validation loops.

### Gap found in this repo

Our policy already says interaction QA must cover all relevant Required Environments, but the actual Run capture schema currently allows only:

```text
SECTION
BOUNDARY
CLUSTER
FULL_PAGE
```

while the template comment already mentions `INTERACTION`.

### Decision

**ADOPT NOW:** make `INTERACTION` a first-class evidence scope and fix the template/schema mismatch.

Future step after a real Reference: introduce an interaction-requirements registry only if actual prototype/behavior evidence shows that automatic coverage validation is worth the added schema complexity.

## 9. Playwright visual comparisons + Trace Viewer — official

Sources:

- https://playwright.dev/docs/next/test-snapshots
- https://playwright.dev/docs/next/trace-viewer
- https://playwright.dev/mcp/tools/tracing

Important details:

- screenshot rendering varies by OS/browser/version/settings/hardware; baselines should be compared in a consistent environment
- `toHaveScreenshot()` takes screenshots until **two consecutive screenshots match** before saving/comparing
- Trace Viewer records action-by-action screenshots, DOM snapshots, network, console, source location and metadata

### Comparison

The Environment Profile + capture lineage model is already stricter than width-only visual regression.

However current `deterministic: true` is a declaration, not yet a proof of settled capture state.

### Decision

**EXPERIMENT CANDIDATE:** `CAPTURE_STABILITY_V1`.

Potential evidence fields:

```text
stability:
  method: CONSECUTIVE_MATCH | HARNESS_ASSERTION | CONTROLLED_MANUAL | OTHER
  sample_count: N
  settled: true|false
  notes: []
```

Do not mandate this until the first real browser harness shows how it works across Safari real-device QA as well as automated Chromium/WebKit runs.

For interaction failures, evaluate Playwright trace ZIP as an optional evidence attachment rather than storing only a final PNG.

## 13. Frontman — browser-first frontend repair

Source:

- https://github.com/frontman-ai/frontman

Frontman works backward from the running browser and exposes:

- live DOM
- computed CSS
- component tree
- source maps
- screenshots
- console/server logs

### Opportunity

This is particularly relevant to **Targeted Repair**, where screenshot mismatch alone may not tell the agent which CSS/component/source owns the rendered problem.

### Decision

**EXPERIMENT CANDIDATE:** `RUNTIME_REPAIR_CONTEXT_V1`.

Possible repair evidence bundle:

```text

+ DOM path / stable locator
+ computed style subset
+ component/source ownership
+ relevant console/network errors
+ screenshot crop
```

Do not install Frontman as a universal dependency. Prefer native project browser tooling or Playwright when equivalent evidence is available.

# Proposed experiment queue after the first real Reference

Do not run all of these at once. Preserve the one-variable principle.

## E-EXT-01 — Pairwise visual preference

Question:

> Does RUN A vs RUN B pairwise visual judgment agree with human review better than absolute automated scores alone?

Keep current `/80` scoring unchanged.

---

## E-EXT-02 — Capture stability

Question:

> Does requiring settled-state evidence reduce false visual mismatches without masking actual animation/state defects?

Compare current deterministic declaration against consecutive-match/harness stability evidence.

---

## E-EXT-03 — Interaction trace evidence

Question:

> For prototype-defined interactions, does preserving before/action/after screenshots + trace reduce silent behavior failures and repair time?

Start with only interactions explicitly supported by the Reference / Company Policy / existing product behavior.

---

## E-EXT-04 — Runtime repair context

Question:

> Does DOM + computed CSS + source ownership evidence reduce repair rounds compared with screenshot-only diagnosis?

Measure repair count and post-First-Pass churn.

---

## E-EXT-05 — Lossy translation warnings

Question:

> Does a structured warning list from the Figma Structure Profile reduce incorrect inference on sections with mixed absolute/Auto Layout, detached components or unsupported effects?

Only promote if repeated across References.

# What not to copy

Avoid these common traps even when popular repos use them:

- one-shot whole-page generation as the production default
- screenshot-only inference when structured Figma evidence exists
- raw pixel score as the only acceptance criterion
- fixed viewport width treated as device identity
- Docker Chromium treated as proof of iOS Safari behavior
- repeated self-repair hidden inside what is reported as “First Pass”
- importing a new visual testing framework into every target repo
- external paper/repo result directly promoted into Company Policy
- final screenshot quality used as proof that the workflow itself improved

---

# Result

The external review **does not justify a major redesign of figma-ai-project**.

The architecture is directionally stronger than most public one-shot systems because it combines Figma structure, existing-code reuse, environment evidence, integration boundaries, First Pass preservation and Clean Replay.

The immediate concrete corrections are deliberately small:

1. monitor Figma Code Connect releases directly;
2. make `INTERACTION` a valid Run evidence scope and remove the template/schema mismatch;
3. preserve the remaining external ideas as explicit one-variable experiments for real References rather than prematurely turning them into permanent rules.
