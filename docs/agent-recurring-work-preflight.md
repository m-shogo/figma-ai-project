# Recurring Agent Work — 新チャット/新案件の開始時チェック

Status: **HUMAN-APPROVED OPERATING CONTRACT**（2026-11-20）
Scope: このrepoで扱う **定期実行・毎時実装・継続作業**。案件個別の技術仕様やセキュリティ規則を上書きしない。
Owner: Human が明示指定。詳細な実行方針は `docs/agent-execution-policy.md`、案件正本は `projects/<slug>/docs/`。

## 0. 新しいチャット・新しい案件の **最初** に確認・指摘する

毎時/毎日/定期スケジュールを新規作成・移管・再開・編集する前、または既存の定期タスクを別チャットで引き継ぐ前に、以下を確認する。

1. **「毎時」= 1時間ごとの起動機会**。1回50分の実行を保証する設定ではない。長時間の連続作業を行う場合は、その実行環境で可能な時間・ツール制限を別途確認する。
2. **「1単位」= 安全な変更/レビュー/コミット/PRの粒度**。1時間に1単位という意味 **ではない**。同じ回で何単位も進めてよい（実行可能なら進める）。
3. 最初に最新の base SHA、open PR、別Agentのowner、最新仕様・QAチェック・既存の学習ログを確認。未マージの先行成果を重複実装しない。
4. **定期タスクの実行履歴**（可能なら開始/終了時刻、成果、阻害要因）を見て、指示が意図どおり実行されているか検証する。起動回数を稼働時間とみなさない。推定作業時間を実測値として報告しない。
5. 初回に Human の期待と仕組みが食い違っている場合は、**作業開始時にこちらから短く指摘**する。Human に「どうして一つしか進めないの？」と言わせるまで待たない。たとえば「毎時は起動頻度で50分稼働の保証ではありません。1回に複数単位を進め、実際の稼働と成果を確認します」。
6. このルールは**案件固有の設定をコピーする指示ではない**。技術実装順・Figma URL/branch/ACF契約・スケジュール自体は新案件で再確認し、新案件に勝手に流用しない。

## 1. 毎回の実行ループ

```text
Current authority / owner / previous run result / open PR を読む（差分優先）
→ 今回の実行で安全に進められる複数の作業を特定
→ Figma・コード・asset・runtime evidenceを確認（必要な場合）
→ 1つの意味ある変更 + 関連QA
→ 小さくcommit / push / PR / CI / merge（安全条件が揃う範囲）
→ 次の独立した作業へ進む
→ 実行環境の上限・真正のBLOCKED・品質上の停止まで続ける
→ 成果・未検証・終了理由・次の一手を記録
```

- **1回の実行中に複数単位、複数commit/PRも可**。ただし関係ない変更を1commitに混ぜない。安全な単位で区切ることと、1回の作業量を制限することは別。
- Figmaのカラー変数1セット・仕様書1枚のような小変更を終えたら、CSS読み込み/見た目の確認、フォント、画像、次のコンポーネント等の **関連する価値ある次工程**に続けて進む。
- CI待ち・外部依存待ちなら、競合しない独立作業へ切り替える。まだ実行できる作業があるのに「1単位終わったから終了」としない。
- 短い実行で成果が少なかった場合、まず実行時間・ツール/権限制約・不要な再調査・過剰な報告・早すぎる終了条件を検証し、**改善できるボトルネック**を次回のループへ反映する。
- 検証不能な状態で無理にmergeしない。静的チェックとWordPress/ブラウザ実機のQAを混同しない。
- 先にプロジェクトの既存規約・チェックシートを活用。毎回全文を再取得するより、変更履歴・前回からの差分を重視する。調査・文書作成だけで終わらず、実行可能な実装とQAを進める。

## 2. 「50分前後」などの時間指定の扱い

- 50分を希望する指示は **品質のためにまとまった作業をしたいという目的**。予定された自動実行に連続50分の実行時間を発生させる機能だと誤認しない。
- 実行プラットフォームが指定できるのは起動時刻/頻度であって、実行継続時間が設定可能とは限らない。実行時間・トークン・コネクタ権限・非同期性を事実として確かめる。
- 適切な別の実行レーン（例:長い作業に向いたWork/専用実装環境）が必要なら、**最初に**利点と制限を短く説明する。勝手に移管・二重稼働はしない。
- 50分を消化するために待機/無意味な操作をしない。50分実行したと根拠なく主張しない。

## 3. 毎回の簡潔なレポート（証拠優先）

- 開始時の正本 SHA、前回との差分/ownership、実際に確認したFigma node等のevidence
- 完了した **複数の実作業**、検証結果（PASS / FAIL / 未検証）、変更先commit/PR/mergeのURLと最新SHA
- 次へ進めなかった **実際の理由**（時間上限、権限、CI/依存、品質上のBLOCKED等）。推測は推測と明記
- 今回見つけたミス・原因・再発防止（案件 `LEARNINGS.md` / QA checklistへの反映）、次回の最優先作業
- 開始/終了時刻が取れる場合だけ正確な所要時間を書く。未取得なら「不明」。起動間隔からの逆算は禁止

## 4. Human FB と実測エビデンス（2026-11-20）

- ニュージャージー補習授業校 `jwsnj` の初期毎時実装で、**カラー変数を1単位として終了**。Human: 「もっと作業出来なかった？」「1時間1単位じゃない、何単位もやっていい」。
- その実行の記録は **2026-11-20 19:32:57〜19:34:11 JST、約74秒**。毎時の起動設定と約50分の作業目標が混同されていたことを確認。ただし**1回の記録から、すべての実行が74秒に制限されると推定しない**。
- 再発原因: ①小さいコミット単位を作業回の終了条件と取り違えた、②稼働実績を確認せず50分目標と説明した、③次へ進まなかった理由を明確に報告しなかった。
- 防止: 開始時に起動頻度≠継続時間を明言、実行履歴を確認、同じ回で複数の安全な変更を進め、実行終了条件を記録。
- 類似のHuman FBが新チャット・新案件で出たときは、まずこの文書を参照して**Humanに再説明・再指示させる前に**最初の時点で指摘・改善する。

## 5. このルールの適用範囲と限界

- **Gitは共通記憶の正本**。新しいAgent/チャットでrepoの`AGENTS.md`と本書を読むことが、運用の再現性の条件。
- このドキュメントをコミットしただけで**ChatGPTの全チャットへ強制配信されるわけではない**。Gitにアクセスできない会話や別repoには自動適用されない。別案件へ移す場合、開始時にリンクして読む/対応するrepoへ明示的に導入する。
- このHuman-approved運用上の規約は `docs/agent-human-fb-weak-spots.md` の W1–W10（UI不具合分類）を勝手に増やすものではない。他の機械的学習昇格規則をバイパスせず、案件の事後評価と両立させる。
